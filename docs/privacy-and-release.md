# Privacy and public release

Public files can be copied, indexed, cached, and retained. Removing a file later does not retract copies or necessarily remove its Git history.

## Keep private context out

Do not publish:

- Names, contact details, account identifiers, organizations, private links, or personal assignments
- Chat transcripts, task exports, meeting notes, emails, screenshots, or internal review records
- Credentials, tokens, recovery details, private configuration, or access instructions
- Filled-in copies of context, autonomy, or decision templates that reveal private accounts, targets, rules, or relationships
- Internal policies, strategies, or commitments that the owner has not approved for public use

Use general principles and clearly synthetic examples. Store instance-specific context in the user's own private project and keep it out of this template's history.

## Before making a repository public

- Confirm the owner and destination repository.
- Review every file and the full Git history for private material.
- Check generated files, hidden files, examples, links, and metadata as well as the main documents.
- Verify which collaborators and integrations have access.
- Select a license deliberately; a public repository is not automatically open source.
- Read back the repository visibility and published contents after release.
